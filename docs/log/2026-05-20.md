# Step 2: puller integration + space-classifier tightening

## What shipped

- **`ACCESS_OWNED_FIELDS` constant** in [frontmatter.py](../../src/sukb/ingest/frontmatter.py) — exported so the puller's frontmatter writer and `merge_preserved_keys` enforce the boundary in code. `merge_preserved_keys` has an explicit assertion that no access field has been mistakenly added to `CLASSIFIER_OWNED_KEYS`.
- **New shared module** [src/sukb/ingest/access.py](../../src/sukb/ingest/access.py) — `PageClassification`, `classify_visibility`, `AncestorRestrictionCache`, manifest serializers, and `rewrite_access_fields`. The probe and the puller import the same code; no duplicate classifier logic.
- **Puller integration** in [src/sukb/ingest/puller.py](../../src/sukb/ingest/puller.py) — `ConfluencePuller.classify_page_access` + `_resolve_account_id`. The per-page loop now:
  1. Classifies access (direct + ancestor + space) before the body-fetch short-circuit.
  2. On version-match skip, calls `rewrite_access_fields` to refresh on-disk frontmatter if the access classification drifted.
  3. On full-pipeline pages, passes access fields into `PageMeta` so the canonical frontmatter writer emits them.
  4. After the loop, writes manifest + spaces.json + sanitized summary to `output/_access/`.
- **Space classifier tightened** in [src/sukb/ingest/spaces.py](../../src/sukb/ingest/spaces.py) per ADR-0008. Positive-ID via `role:ANONYMOUS read/space` marker (present on ITSAI); `unknown` if absent and not in the operator allowlist. Permissions endpoint now paginated.
- **Page-level classifier tightened** in [src/sukb/ingest/access.py](../../src/sukb/ingest/access.py) — `space.default_audience == "unknown"` is treated as `space_restricted` at the page level (vs `skipped`, which still falls through to direct + ancestors).
- **Config knob** `broadly_accessible_spaces` in [sync_config.yaml](../../sync_config.yaml) + [src/sukb/config.py](../../src/sukb/config.py). Defaults to empty — positive ID handles ITSAI without an entry.
- **Probe refactored** to import shared helpers from `access.py` — no logic duplication; the probe is now mostly an orchestrator + CLI wrapper. `rewrite_frontmatter` removed (replaced by shared `rewrite_access_fields`).
- **ADR-0008** [docs/decisions/0008-space-classifier-tightening.md](../decisions/0008-space-classifier-tightening.md) — captures the positive-ID + allowlist decision with concrete evidence from ITSAI's 225 permission records.

## Decisions / changes from the review

The 2026-05-20 review flagged four issues. Each is now addressed:

1. **`FRONTMATTER_SCHEMA_VERSION = 3`** — Done. State-version mismatch forced the full re-ingest on the first puller run today.
2. **Space classifier too permissive** — Done via ADR-0008: positive-ID via `role:ANONYMOUS read/space`, with operator allowlist as documented fallback. `unknown` space → page `space_restricted`.
3. **Clobber risk between Step 1 and Step 2** — Resolved by completing Step 2. The Step-1-bridge defensive measure (adding access fields to `CLASSIFIER_OWNED_KEYS`) was unnecessary since Step 2 landed in the same session.
4. **MCP filter not active** — Acknowledged; Step 3 is next. STATUS.md now says "the corpus is NOT public-query safe until Step 3 ships."

One nuance I pushed back on: the reviewer suggested "manual allowlist" as an alternative to positive ID. I implemented **both** — positive ID first (the common case), allowlist as documented fallback for legitimate exceptions. The allowlist is empty by default; ITSAI doesn't need it.

## Surprises

- **`role:ANONYMOUS` marker on ITSAI** — when I dumped the ITSAI permissions payload to look for a positive-ID signal, this was the unambiguous needle. It's stable Atlassian API surface (documented as the "anyone the site lets in" principal). Better than enumerating SU group GUIDs.
- **Second sync still takes 35s for 34 pages** — that's the cost of refreshing access on every sync per ADR-0007 (~2 calls per page × 200ms rate-limit ceiling = ~14s API time + OneDrive file I/O). At 4000 pages this is ~70min; the plan's "cache restrictions to disk with TTL" is a real Phase 1.5+ concern. Not a blocker today.
- **`page_skipped` events now carry `access_rewrite` + `visibility_signal` payload fields** — caught when I checked the second-sync events. The web UI's SSE listener might need to handle the new fields when displaying skip reasons. Not load-bearing for v1.5 eval work but worth flagging.

# Step 3: MCP / indexer read-path filter

## What shipped

- **`load_raw_corpus` filters by `visibility_signal`** in [src/sukb/chat/query.py](../../src/sukb/chat/query.py). Public allowlist is the canonical string `no_read_restrictions_seen`; legacy `accessible_to_sync_user`, `unknown`, missing, and every restricted variant are filtered. `include_restricted=True` is the explicit escape hatch for admin / puller paths.
- **`load_wiki_corpus` drops hubs whose `synthesizes` references a non-public page.** The hub body may contain citations / paraphrases of the restricted source — partial filtering would still leak. Added `WikiHub.restricted_source_ids` for audit observability under `include_restricted=True`.
- **`extract_citations` distinguishes restricted from unresolved.** A `[[<restricted-id>]]` in the model's answer resolves to `(restricted — not available)`; a `[[<missing-id>]]` resolves to `(unresolved)`. Both hide title + URL — same content-protection outcome, more useful operator signal.
- **`AgenticTools` wires the filter + defense-in-depth.** `__init__` passes the public-allowed-ID set to `load_wiki_corpus`. `_source_pages_for_hub` surfaces `(not available)` for any synthesizes ID not in the public set, even if a polluted hub slipped through load. `_read_page` returns the SAME external "ERROR: no raw page" for restricted IDs as for nonexistent ones (no enumeration oracle); the trace summary annotates `(restricted)` for eval observability only.
- **`ADR-0009`** [docs/decisions/0009-mcp-read-path-filter.md](../decisions/0009-mcp-read-path-filter.md) — captures the load-time-vs-query-time choice with the parity table for restricted vs nonexistent responses across all five surfaces.

## Verification

- **253 / 253 tests pass.** 27 new in [tests/chat/test_step3_filtering.py](../../tests/chat/test_step3_filtering.py) covering: load-time filter on every non-public value (parametrized including the legacy `accessible_to_sync_user`), wiki-hub drop, `(restricted)` vs `(unresolved)` citation paths, `search`/`read_page`/`list_hubs`/`list_index`/`_source_pages_for_hub` all reject restricted, trace-summary observability, and the Summer Intern fixture round-trip from the plan's test matrix.
- **Real-corpus check:** with the `_is_test_page` path-segment exclusion disabled (`include_test_pages=True`), the visibility filter ALONE excludes the 3 Summer Intern pages (`1068171339`, `1069318154`, `1069350926`) and admits 31 clean pages. Confirms the path-segment exclusion is now genuinely redundant for the Summer Intern case — the follow-up ADR can remove it after the plan's two-week soak.
- **Smoke run against live AgenticTools:** `read_page('1068171339')` → `ERROR: no raw page with page_id='1068171339'` (same shape as a nonexistent ID). `search(query='Julian making sure create new documents')` → top hits are unrelated mentorAI pages; no Summer Intern leak.

## Surprises

- **Existing chat test fixtures didn't include `visibility_signal`** — they default to `unknown` under the new loader and got filtered, breaking 9 tests. Fixed by adding `visibility_signal: no_read_restrictions_seen` as the test fixture writer's default. Surfaces an interesting invariant: any future fixture that omits the field auto-fails the public gate, which is exactly the safety property we want at the read path.
- **`load_raw_corpus(include_restricted=True)` is called twice during `answer_query`** — once for the public list, once to derive `restricted_page_ids` for citation resolution. Could be one pass with two outputs; deferred — the disk walk is small (~34 files) and the readability win of two named calls outweighs the I/O savings.
- **`AgenticTools.__init__` now loads the corpus three times** — public, restricted-included for drop count, restricted-included for `_restricted_raw_ids`. Same observation as above; small corpus, deferred consolidation.

## Operator-visible changes

- The corpus citation panel in the chat UI now shows `(restricted — not available)` for restricted-ID citations. Was `(unresolved)`. The UI consumes `extract_citations` output directly, so this surfaces automatically — no UI code change needed today.
- `AgenticTools` exposes `dropped_hub_count` as an instance attribute. The agentic eval can log this per-run to detect hub-pollution regressions.
